# Publish moves through per-filesystem staging directories, with no journal

A move writes its copy to a named temp file (`O_CREAT|O_EXCL`) inside a staging directory at the root of the destination filesystem. It `fsync`s the file and publishes it into place with `renameat2(RENAME_NOREPLACE)`. Retiring the source likewise renames it into the cache branch's staging directory before it is unlinked. The filesystem itself is the only state: every step is idempotent, so crash recovery means listing each staging directory and resolving each leftover against its published counterpart, and then simply running again. A retired source is deleted if it is identical to its published counterpart and not in use, and renamed back otherwise. A temp file is always deleted: a source is retired only after its copy is published, so a temp file is never the only copy, and renaming a partial one into place could expose a truncated file.

## Considered options

- **`O_TMPFILE` + `linkat`.** It leaves nothing behind after a crash, but on OpenZFS the link is not ZIL-logged and waits for a full transaction-group sync, which takes seconds per file.
- **An intent journal.** It finds leftovers exactly, but it is a second source of truth to keep consistent. The filesystem state already determines the correct recovery (a duplicate relpath is just a stale copy), so the journal would only locate leftovers, and a staging directory does that too.
- **Temp files next to the destination, found by name pattern.** This is upstream's approach. It deletes user files that happen to match the pattern, and finding them needs a walk of the whole backing pool.

## Consequences

- Each staging directory is visible at the root of the cache pool while a run is active, or after a crash until the next run. cachy removes it once it is empty.
- A directory that cachy creates on a branch is built with its metadata in `<staging directory>/.cachy-staging`, which mirrors no relpath, and renamed into place with `RENAME_NOREPLACE`, so it never shows without its metadata. Recovery removes such a directory if a crash leaves it behind, empty. Its mtime is set only at the end of the run, which keeps no record of it: after a crash, the directory keeps the mtime of its last change.
- A branch with nested filesystems (for example child ZFS datasets) gets one staging directory per filesystem, because renames cannot cross filesystems.
- A crash between publish and retire leaves no leftover, only the relpath on both branches. Recovery cannot find this without walking the backing pool. The next move of that relpath finds an identical stale copy at the destination, by size, metadata and content before copying anything, and keeps it as the published copy.
- A move replaces a differing stale copy with `renameat2(RENAME_EXCHANGE)`, which swaps the staged copy in. The swapped-out file then sits in the staging directory under the temp file's name. The move checks that it is the stale copy it inspected when it started (same device, inode, type, size and mtime), and then deletes it. Otherwise it swaps the file back, so a move never overwrites a file it has not inspected. After a crash, recovery deletes the swapped-out stale copy as a temp file. One gap remains: if the swap back fails, or cachy crashes before it, the file that came out stays under the temp file's name, and the next recovery deletes it as well. That needs a file that changed between the inspection and the swap, and a fault in that short window. A stale copy on another branch is removed after publish and before retire, so the relpath never disappears from the cache pool. A rollback cannot restore a replaced or removed stale copy. This loses nothing that applications could see: the stale copy was hidden, and a move never replaces one that is newer than the source. A newer one may hold an edit made through the cache pool while a move's source waited in its retire, if recovery then renamed the source back. Files whose mtime is set back on purpose, for example by `cp -p` or `rsync -a` onto the cache pool, trip this rule as well. Such a relpath fails every run until someone removes the copy that is out of date, which costs a manual step but loses nothing.
- A symlink cannot be fsynced, so a symlink move makes its copy durable by fsyncing the directories that hold it. On ext4 and XFS that commits the copy's owner and timestamps too; on ZFS it may not. A crash within seconds of a symlink move can then leave the published symlink with its link text intact but with cachy's owner and the time of the move. Its source is gone by then, so recovery has nothing to restore them from. Syncing the whole backing filesystem before retiring symlinks would close this window, but costs too much for how rarely it matters.
- A hardlink group is copied once and published under its first name; each further name is then linked to it (`linkat` never replaces either). Its names are retired together, under the one lease. A crash between names leaves some published and some still on the cache branch, or some retired: recovery deletes a retired name that is identical to its published counterpart, and the next move of the names left on the cache branch adopts the published copy and the links already there, and links any missing names to it.
- cachy never writes to a backing branch that takes no new files (mergerfs mode `RO` or `NC`), not even to recover. Leftovers in its staging directory stay there, with a warning on every run, until the branch takes new files again.
- Every filesystem that cachy writes to needs `RENAME_NOREPLACE`, and a backing branch also `RENAME_EXCHANGE`; filesystems without them (for example OpenZFS < 2.2.0, which has neither) are unsupported. The capability probe tries both on scratch files in the staging directory before every invocation, and refuses to run without them. Its scratch files live in `<staging directory>/.cachy-staging`, under a name prefix of their own, since it mirrors no relpath; the next probe removes any that a crash left there, before recovery could take one for a retired source.
